# Data Migration plan

The DevKit owns encrypted external MariaDB source connections, named migration sessions, table-pair child rows, field-pair child rows, transfer validation, batch execution, and run history. Each session has an API-generated UUID, a name, source and destination database snapshots, and validated tenant references. Table-pair rows carry source/target names, row-count snapshots, mapping status, and migration status. Field-pair rows carry source/destination names, mapping status, and the actual operator. Migration Settings owns the UI for external host, port, database, user, TLS, and saved secret changes. Platform supplies Super Admin identity, registered destination tenant database connections, tenant lookups, master lifecycle composition, and desk navigation. Batch migration requires mappings for every source table, validates the complete job before writing, and runs all table inserts in dependency order inside one destination transaction. Destination tables must exist and be empty. Source connections are read only. Before execution, generate a persisted review plan with parameterized query templates and source-data fingerprints, then require an explicit finalize action. Execution recomputes the plan and rejects stale changes; SQL templates are never accepted as executable browser input. Current sample-row selections do not restrict batch rows. Future larger migrations require a durable queue and resumable checkpoints beyond the current 10,000 row per table bound.

The Platform composition adapter may supply its configured MariaDB server connection to Migration Settings as a source preset. Only host, port, and username are returned to the browser; the API tests and encrypts the server-side password. Database discovery continues to exclude the Platform master database.

The audit handoff queue persists one SQL dump snapshot and redacted selected sample data per mapped table pair. The list route returns queue summaries; opening an item loads the raw SQL template and sample data on a separate detail page. Handoff requires saved row samples and a saved mapping for that pair, not mappings for every source table. The API composes identifier-quoted SELECT statements and parameterized INSERT templates from the saved mapping and sample selection. Sample row positions are review context only, not stable source record keys; queue review is separate from plan finalization and execution.

Before production use, verify schema upgrade on an existing master, two disposable tenant databases, rollback on conflict, super-admin denial, and the Super Admin browser desk.

Audit checkpoint: the public transfer execution action is restricted to the reviewed Migration Queue route. Migration Analysis and Transfer Review cannot run a copy directly; legacy plan table data remains untouched for compatibility. Remaining review findings: saved audit sample JSON is currently accepted from the browser instead of being re-read from the source; custom/default/foreign values shown by the sample builder are not applied to the full-session migration; target emptiness can race unrelated tenant writers because the migration lock is not shared with application writes; destination commit and master-ledger status updates are not atomic; and the 10,000-row table bound has no resumable queue. Resolve these before treating the feature as a robust production migration service.
