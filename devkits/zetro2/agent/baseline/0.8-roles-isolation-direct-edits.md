## 2. Workspace Isolation Architecture

Multi-workspace security is enforced at both data and runtime layers:

```text
+---------------------------------------------------------------------------------+
|                                 Zetro2 API Host                                 |
|                                                                                 |
|  [Incoming HTTP / WebSocket]                                                    |
|           │                                                                     |
|           ▼                                                                     |
|  ┌───────────────────────────────────────────────────────────────────────────┐  |
|  │ Authenticate: Validate JWT / Session Token via LocalIdentityManager       │  |
|  └─────────────────────────────────────┬─────────────────────────────────────┘  |
|                                        ▼                                        |
|  ┌───────────────────────────────────────────────────────────────────────────┐  |
|  │ Resolve Membership: Lookup (actor_id, workspace_id) in SQLite             │  |
|  │ Assert: Membership is ACTIVE and not expired                              │  |
|  └─────────────────────────────────────┬─────────────────────────────────────┘  |
|                                        ▼                                        |
|  ┌───────────────────────────────────────────────────────────────────────────┐  |
|  │ Authorize: Evaluate actor permissions vs route requirements               │  |
|  │ Reject with 403 Forbidden if required grants missing                      │  |
|  └─────────────────────────────────────┬─────────────────────────────────────┘  |
|                                        ▼                                        |
|  ┌───────────────────────────────────────────────────────────────────────────┐  |
|  │ Database Query: Append WHERE workspace_id = :workspaceId to all queries   │  |
|  └───────────────────────────────────────────────────────────────────────────┘  |
+---------------------------------------------------------------------------------+
```

### 2.1 Data-Layer Isolation
- All domain tables (`tasks`, `epics`, `agent_runs`, `memory_documents`, `audit_events`, `approvals`) carry an indexed `workspace_id` column.
- Cross-workspace queries are strictly prohibited; foreign keys must resolve within the same workspace scope.
- Database access repositories enforce `workspace_id` filtering on all CRUD operations.

### 2.2 Container and Filesystem Isolation
- Editor sessions connect to a sandboxed workspace directory.
- Reviewer and Viewer roles mount the workspace filesystem with read-only flags (`:ro`), preventing any file writes or deletions.
- Interactive terminal instances are restricted to authorized roles with `process.execute`.
- Docker sockets are never exposed to workspace containers.

## 3. Direct Edit Behavior and Human-Agent Concurrency

A core design principle of Zetro2 is that **human developer edits take precedence over agent proposals**:

### 3.1 Workspace Write Leases
- When an agent coding run begins modifying files, it requests a time-bounded `WriteLease` on the target paths.
- The write lease identifies the run ID, target file set, and lease expiry timestamp (default 120 seconds, heartbeated).
- The lease does **not** block human developer edits; it exists to notify the agent if a human modifies the files concurrently.

### 3.2 Human Edit Detection & Unsaved Buffer Protection
- Before applying any file modification:
  1. The agent checks the file's current disk hash against the baseline hash recorded when the run started.
  2. The agent queries the ZVcode extension bridge for unsaved/dirty buffer state on the target file.
- If the file has been modified on disk by the user, or if an unsaved buffer exists:
  - **No Silent Overwrite:** The agent immediately suspends automatic write operations.
  - The agent generates a structured `DiffConflictProposal` rather than modifying the file on disk.
  - The conflict is presented in the ZVcode chat/diff review card with options:
    - *Accept Human Version* (agent re-plans against user changes).
    - *Apply Agent Patch to Buffer* (user manually reviews and merges).
    - *Abort Run*.

### 3.3 Conflict-Free State Transitions
- Agent progress and task completion checkboxes are updated only after verification passes and the working tree is reconciled.
- Unsaved human edits are never discarded or committed by automated agents.

## 4. Backend Permission Requirements & Gates

Every API route and event handler enforces declarative security gates:

### 4.1 Request Pipeline Gates
1. **Authentication Gate:** Requests must provide a valid session token in `Authorization: Bearer <token>` or session cookie.
2. **Workspace Scope Gate:** The request path or header must specify `X-Workspace-Id`. The server resolves the actor's membership in that workspace.
3. **Capability Gate:** The endpoint declares required permissions (e.g. `[workspace.write, agent.run]`). `authorize(actor, requirement)` evaluates the effective set.
4. **Approval Gate (High-Risk Actions):**
   - High-risk operations (e.g. `process.execute` with elevated privileges, external `git.push`, dangerous tool executions, budget overrides) require a cryptographically bound `ApprovalToken`.
   - The token encodes:
     ```json
     {
       "action": "git.push",
       "workspaceId": "ws-123",
       "actorId": "usr-456",
       "contentDigest": "sha256:abcd...",
       "expiresAt": "2026-09-24T12:30:00Z"
     }
     ```
   - Tokens are single-use and expire within 5 minutes.
5. **Session Revocation & Kill-Switch:**
   - When a user's membership is changed or revoked, active WebSocket connections and active agent runs for that actor in that workspace are immediately aborted.
