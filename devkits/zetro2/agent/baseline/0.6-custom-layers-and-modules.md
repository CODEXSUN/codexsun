## 1. The Four Custom Editor Layers

Rather than maintaining a separate fork or accepting opaque upstream images, Zetro2 owns its customized editor source (`devkits/zetro2/zvcode`) and structures customizations into four distinct, audited layers:

```text
+-----------------------------------------------------------------------+
|  Layer 1: Product Layer (Branding, Identity, Settings, Extensions)    |
+-----------------------------------------------------------------------+
|  Layer 2: Access Layer (Session Binding, Workspace Mount, Roles)      |
+-----------------------------------------------------------------------+
|  Layer 3: Chat Layer (Native Chat, Context, Tool Cards, Approvals)    |
+-----------------------------------------------------------------------+
|  Layer 4: Runtime Bridge (Typed HTTP & Resumable WebSocket IPC)       |
+-----------------------------------------------------------------------+
```

### 1.1 Layer 1: Product Layer
- **Responsibility:** Branding, user-facing identity, workbench defaults, and built-in extension configuration.
- **Key Modifications:**
  - `product.json`: Configures `nameShort: "ZVcode"`, `nameLong: "ZVcode"`, `applicationName: "zvcode"`, `serverApplicationName: "zvcode"`, `dataFolderName: ".zvcode"`, `urlProtocol: "zvcode"`.
  - Disables upstream telemetry, telemetry endpoints, and crash reporters.
  - Custom welcome screen suppression (`startupEditor: "none"`).
  - Status bar branding: "Codexsun ZVcode" / "Zetro2".
  - Configures built-in extension whitelist and blocks untrusted marketplace extension installations in restricted profiles.

### 1.2 Layer 2: Access Layer
- **Responsibility:** Binding editor web/WebSocket connections to verified Zetro2 sessions, workspace scopes, and role permissions.
- **Key Capabilities:**
  - Token-authenticated connection handshake with Zetro2 API (`/api/v1/zetro2/editor/connect`).
  - Enforces workspace isolation: verifies the connecting actor is authorized for the attached `workspaceId`.
  - Enforces role capabilities:
    - *Developer / Maintainer / Owner:* read-write workspace mount, full interactive terminal, file save permissions.
    - *Reviewer / Viewer:* read-only filesystem mount, disabled file save, terminal disabled or restricted to read-only replay, extension host sandboxed without write access.
  - Mid-session revocation hook: immediately terminates editor WebSocket and kills spawned processes upon membership revocation.

### 1.3 Layer 3: Chat Layer
- **Responsibility:** Refactoring native VS Code chat and inline-chat surfaces to communicate with Zetro2 agent execution.
- **Key Capabilities:**
  - Replaces third-party Copilot service endpoints with Zetro2-managed Model and Agent adapters.
  - Exposes Ask, Plan, and Code execution modes.
  - Model and backend selection in the chat header (e.g. Claude 3.5 Sonnet, GPT-4o, Gemini 1.5 Pro, OpenCode, OpenHands).
  - Renders interactive structured cards:
    - Context snapshot breakdown (files, symbols, git diff, rules).
    - Tool invocation proposals with diff views and execution parameters.
    - Explicit human approval actions (Approve / Reject / Modify).
    - Test execution output and criterion evidence verification status.

### 1.4 Layer 4: Runtime Bridge
- **Responsibility:** Two-way typed communication between the ZVcode workbench/extension host and the Zetro2 control plane.
- **Key Capabilities:**
  - Typed HTTP client for initiating runs, querying tasks, submitting reviews, and requesting approvals.
  - Resumable WebSocket connection for streaming execution events, live terminal output, file change notifications, and progress ticks.
  - Reconnect cursor and sequence tracking to recover dropped connections without missing events or duplicating actions.

## 3. Public Interfaces & Contract Boundaries

Modules communicate exclusively through versioned public contracts, events, and provider interfaces:

```text
+------------------------------------------------------------------------------------+
|                                 Zetro2 Web & API                                   |
|                                                                                    |
|  +--------------------+     Contracts      +--------------------+                  |
|  |  Workspace Access  |<-------------------|  Work Management   |                  |
|  +--------------------+                    +--------------------+                  |
|            ^                                         |                             |
|            | Grants / Policy                         | Task & Criteria             |
|            v                                         v                             |
|  +--------------------+     Evidence       +--------------------+                  |
|  | Integrations &     |<-------------------|  Coding & Execution|                  |
|  | Workspace Runtime  |                    |  (Runs, Diffs, Ev.)|                  |
|  +--------------------+                    +--------------------+                  |
|            |                                         |                             |
|            +-------------------+---------------------+                             |
|                                v                                                   |
|                    +-----------------------+                                       |
|                    | Knowledge Module      |                                       |
|                    | (Memory Bank Engine)  |                                       |
|                    +-----------------------+                                       |
+------------------------------------------------------------------------------------+
```

### 3.1 Contract Principles
1. **Separation of Task and Run:**
   - `Task` belongs to `work-management`. It represents *what needs to be accomplished*, requirements, and acceptance criteria.
   - `AgentRun` belongs to `coding`. It represents *what an agent attempt did*, tool calls, diffs, and verification commands.
   - `work-management` reads verification evidence produced by `coding` to evaluate acceptance criteria; it never writes to run tables.
2. **Reused Shared Primitives:**
   - Leverages `@codexsun/platform-core` for:
     - `Actor`, `Role`, `Permission`, `identitySessionSchema`
     - `authorize(actor, requirement)`
     - `readLocalIdentityConfiguration`, `createLocalIdentityManager`
     - `SqliteDataProvider`, `MigrationIntegrityRecord`, `MigrationRunner`
3. **Domain Event Bus:**
   - Asynchronous domain events published via transactional outbox (`database-outbox.ts`).
   - Events include: `task.created`, `task.transitioned`, `run.started`, `run.completed`, `evidence.recorded`, `approval.requested`, `approval.granted`.
