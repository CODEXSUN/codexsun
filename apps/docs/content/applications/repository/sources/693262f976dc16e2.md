# Data Bridge 1.1.54: cloud staging handoff

## Readiness decision

The local implementation is ready for cloud staging verification.
Cloud production import acceptance remains pending.
The operator will deploy this source release and configure the remote database connections.
This handoff does not deploy services, create remote databases, or run remote imports.

## Verified local baseline

Read [RELEASE-1.1.53.md](RELEASE-1.1.53.md) for complete local evidence.
Both actual browser actions completed in Common → Masters → Billing order.
SUKRAA preserved 1,978 existing rows and two approved differences.
ALTEX preserved 5,471 existing rows without warnings.
No inserts were needed because both targets were already complete.
All 321 invoices and 1,211 item rows matched after target foreign ID translation.
Ten e-invoices, nine e-way bills, and five deleted ALTEX invoices retained their business data.
Independent checks found zero missing records and zero broken references across 354 relationships.
Fresh backups and disposable restores verified 545 tables.
All 14 focused tests passed for the runtime release.

## Database compatibility

This release adds no new migration or business-data change.
Cloud installations must apply the existing additive Data Bridge v6 migration if it is absent.
It creates the run and invoice verification storage used by the split reports.
Retain earlier migration ledger keys and checksums.
Apply the target owners' required Core and Billing migrations before importing their business records.
Do not rebuild, empty, or replace existing client business tables.

## Operator deployment sequence

1. Deploy the pushed 1.1.54 source release with the repository deployment process.
2. Resolve database hosts and secrets from the running cloud API environment.
3. Verify consistent backups and a disposable restore before cloud migrations or writes.
4. Run the repository migration preflight and required owner migrations.
5. Enable the Queue Manager worker with `CODEXSUN_QUEUE_WORKER_ENABLED=1`.
6. Verify API readiness, Super Admin authentication, and tenant routing.
7. Create saved remote source connections and register the intended destination tenant databases.
8. Verify each pair through Data Bridge → Database Connection.
9. Rehearse the complete operation against an owned remote target clone.
10. Review the clone's table, row, foreign ID, invoice, and warning results.
11. Authorize the exact real remote pair and missing-only import scope.
12. Run the real action and verify its persisted queue and report evidence.

Store database credentials through the supported server-side connection and secret configuration.
Use supported TLS verification and restricted database network access.
Keep passwords, dumps, and authentication cookies out of Git and release logs.
Connectivity alone does not prove an import or queue worker is healthy.

## Remote acceptance gates

- [ ] Confirm the deployed source version and API readiness.
- [ ] Verify backup checksums and a disposable restore for the approved remote pair.
- [ ] Confirm Data Bridge v6 and the target business schemas are present.
- [ ] Verify source and target connectivity from the cloud API environment.
- [ ] Verify one real target-scoped queue job finishes and persists its report.
- [ ] Confirm Common → Masters → Billing order and missing-only behavior.
- [ ] Verify complete invoices and children after destination foreign ID translation.
- [ ] Verify Summary, Common, Masters, Billing, Invoices, and Warnings tabs independently.
- [ ] Confirm repeated processing adds no duplicates and preserves existing business data.
- [ ] Record every new remote warning and obtain a decision before any correction.

The previous SUKRAA approvals do not authorize new remote data corrections.
Do not mark these gates complete from local tests, builds, a healthy route, or a successful login.

## Transaction and rollback boundary

Imports commit per table. There is no single transaction across an entire invoice.
Conflicting existing records remain unchanged and produce warnings.
New dependent records wait when a required parent needs review.
Provider jobs, permissions, roles, caches, and runtime history remain outside business import scope.
Use verified backups and the owner's recovery procedure for an approved rollback.
