# Q Cafe Windows application

## Desktop-first Platform connection plan

Status: planned. The current desktop uses local SQLite and separate license activation.
It does not yet enroll with Platform or synchronize restaurant records with MariaDB.
The Platform QCafe web menu and POS now use tenant MariaDB. Desktop enrollment and synchronization remain planned.

### Target scope

- Focus on the installed QCafe desktop. Defer changes to the hosted restaurant UI.
- Run Platform in multi-tenant mode. Platform owns tenant identity, user identity, activation, and device access.
- Bind one desktop installation to one tenant. A tenant can enroll multiple desktop devices.
- Keep restaurant operations in local SQLite so approved workflows can work without a network.
- Store cloud restaurant records in the selected tenant MariaDB database through QCafe-owned APIs.
- Keep the desktop away from direct MariaDB connections and database credentials.
- Keep QCafe business behavior in QCafe. Platform owns only identity and device lifecycle infrastructure.

### 1. Online enrollment and identity

1. Open the trusted Platform sign-in flow and require Corporate ID in multi-tenant mode.
2. Authenticate the Platform user and verify tenant status, QCafe activation, and device enrollment permission.
3. Register a device under the authenticated tenant through an explicit Platform device contract.
4. Return server-issued tenant UUID, device UUID, allowed company scope, and enrollment status.
5. Store device secrets in Windows Credential Manager through Rust. Store only non-secret workspace identity in SQLite.
6. Require the local API to validate the enrolled workspace before opening its business database.
7. Reject tenant changes through local settings, request headers, imported files, or changed database paths.

License activation remains separate from tenant enrollment. A license key must not select a tenant or grant permissions.
Do not reuse browser cookies, license tokens, or the local operator token as cloud device credentials.
Initial enrollment requires connectivity. Existing standalone data requires a backed-up, explicit ownership adoption flow.
Do not silently upload existing restaurant records into the first tenant that signs in.

### 2. Local workspace and staff identity

Partition local storage by enrolled tenant and device. Preserve existing databases until ownership adoption succeeds.
Bind each local business store to immutable enrollment metadata and validate that binding on every startup.
Keep data, images, backups, and synchronization state inside the same workspace boundary.

Platform owns cloud users. QCafe owns restaurant staff and local PIN authentication.
Define explicit mappings between staff and Platform users where cloud access is needed.
A cashier PIN must not become a Platform login. Never synchronize raw PINs or device secrets.
Tenant replacement must block while unsynchronized work exists and require an explicit recovery or transfer procedure.

### 3. Tenant cloud persistence

Add module-owned MariaDB migrations, repositories, services, contracts, permissions, and audit records for QCafe business entities.
Resolve tenant storage from authenticated Platform identity on every cloud request.
Replace the current cloud SQLite adapter for migrated entities without changing the local desktop SQLite runtime.
Define stable public UUIDs and mappings independently of local integer primary keys.
Do not copy local integer IDs into cloud foreign keys or merge tenant datasets by matching row numbers.

### 4. Offline authorization

Online requests retain live Platform tenant, device, user, activation, and permission checks.
Cached login or workspace metadata must never authorize an offline operation.
Design an explicit, signed, time-limited offline capability contract before enabling offline writes.
That contract must define allowed actions, staff scope, expiry, clock rollback handling, and reconnect behavior.
Update the authoritative authentication rules with the implemented contract and its verification tests.
Until this contract exists, Platform-connected offline writes remain disabled.

Start with approved POS, receipt printing, and payment recording workflows.
Keep tenant administration, device enrollment, role changes, and destructive maintenance online-only.
Document that remote revocation cannot reach a disconnected device immediately.
Choose the offline validity period explicitly before release. An expired grant must preserve unsynchronized data.

### 5. Reliable synchronization

Write each business operation and its outbound event in one local SQLite transaction.
Use stable operation IDs, device UUIDs, record versions, correlation IDs, and ordered device sequence numbers.
Synchronize through authenticated tenant-bound APIs with durable acknowledgments, retries, and resumable download cursors.
The cloud must verify tenant and device ownership and deduplicate retries before applying a transaction.
Validate synchronized operations against the agreed offline capability and reconciliation policy.
Do not silently discard authorized offline sales after a later permission change.

Download approved master and configuration changes. Upload local transactions and audit events.
Treat finalized bills and payments as immutable. Use explicit adjustments or reversals for corrections.
Apply inventory movements as events rather than replacing stock totals.
Define device-scoped bill numbering and explicit master-record conflict rules.
Quarantine rejected operations with a recoverable reason. Never mark them synchronized before durable cloud acknowledgment.
Use the Platform queue for slow cloud processing and a durable desktop worker for local delivery.

### Delivery gates

1. Enrollment: prove two tenants cannot enroll, access, or synchronize each other's workspace.
2. Persistence: prove QCafe cloud records use tenant MariaDB while desktop records use SQLite.
3. Offline operation: disconnect, transact, print, restart, and recover without losing approved work.
4. Synchronization: prove retry deduplication, interrupted recovery, dependency ordering, and conflict handling.
5. Lifecycle: prove device revocation, grant expiry, staff restrictions, backup recovery, and blocked tenant replacement.

Implement enrollment first. Then deliver one complete POS bill and payment synchronization workflow before expanding to other modules.

The React frontend is developed in a browser and packaged into a Tauri Windows application. The web and Windows builds use the same Q Cafe screens and PIN flow. Tauri adds local data-folder selection, SQLite backup and API startup, licensing, updates, and Windows receipt printing.

## Development

Run commands from the repository root:

```powershell
npm.cmd run dev:qcafe
npm.cmd run dev:qcafe:windows
```

`dev:qcafe` starts only the Q Cafe API and Vite frontend. Open `http://127.0.0.1:5180/qcafe/` for browser development. `dev:qcafe:windows` runs the Tauri host against that same Vite URL. Tauri starts the two services through its `beforeDevCommand`. Development requires `CODEXSUN_TENANCY_MODE=single` in the root `.env`.

The browser build uses the `/qcafe/` base path for the Platform proxy. The desktop build uses `/` so Tauri can load packaged assets from its own origin. The frontend calls the loopback API at `127.0.0.1:4180` in Tauri. In a release build, Rust extracts the API source and migrations, starts the bundled Node runtime, and keeps the API's operator token private to the process. Staff still sign in with their Q Cafe PIN or username.

## Packaging

Run `npm.cmd run build:qcafe:windows` from the repository root. It builds the desktop frontend, Rust host, and Rust print service, then requests both NSIS and MSI installers. It stages the current Windows Node executable under root `dist`. Tauri builds the print service from `src-tauri/src/bin/qcafe-print-service.rs` and bundles it alongside the host.

The installer carries `node.exe`, the print-service executable, and its installer script. Generated executables stay outside Git; the print-service Rust source is tracked. Q Cafe's release number is `1.0.38` in `version.json`, Tauri configuration, and Cargo metadata; npm workspace package versions follow the CODEXSUN root version.

The update command now looks for `qcafe-update.json` in the current CODEXSUN GitHub release. Publish a matching update manifest and installer asset before enabling update checks for customers. `CODEXSUN_QCAFE_UPDATE_MANIFEST_URL` can select a different trusted feed.

## Local data

On the first release launch, Q Cafe asks for a durable data folder. The SQLite database, images, backups, and API log live there. The Rust host keeps the selected folder in the user's application settings and makes a daily SQLite backup before API startup. Installing a new application version does not replace this data folder.
